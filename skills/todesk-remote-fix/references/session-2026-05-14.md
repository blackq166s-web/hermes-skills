# Session: ToDesk Remote Fix — Full Diagnostic Trace

**Date:** 2026-05-14

## Initial Symptom
User trying to remote into this Mac from another computer via ToDesk. ToDesk shows as offline / can't connect.

## Diagnostic Path

### Phase 1: Process Check
- ToDesk_Service (PID 1458, root): Running since Friday ~5 days ago
- ToDesk GUI (PID 5103): Fresh (user restarted GUI)
- All processes present and alive

### Phase 2: Network Check (Initial False Positive)
- `lsof -iTCP | grep todesk | grep -v 127.0.0.1` → EMPTY
- **Initial diagnosis (WRONG):** Service network stack dead after 5-day uptime
- Tried: kill root service (no sudo), launchctl kickstart/bootout, AppleScript admin, CoreGraphics clicking, config.ini manipulation, DNS flush, WiFi toggle — ALL FAILED

### Phase 3: The Breakthrough
- User came to the computer, configured passwordless sudo for `killall -9 ToDesk_Service`
- Killed ALL ToDesk processes → fresh restart
- **Freshly started Service STILL had zero outbound connections!**
- This disproved the original hypothesis (service uptime was not the cause)

### Phase 4: System Network Check
- `curl https://httpbin.org/ip` → FAILED (system-level network issue)
- `nslookup baidu.com` → WORKED (DNS fine, TCP blocked)
- `netstat -rn -f inet` → REVELATION:
  ```
  128.0/1  →  198.19.0.1  via utun4    ← BLACK HOLE!
  ```
- `ifconfig` → 10+ `utun*` interfaces still UP
- No proxy process running (Clash/Surge/Rocket all absent)

### Root Cause
A VPN/proxy app (likely Clash or Shadowrocket) was quit but left its **split-routing rules** active. The `128.0/1` route sends half of all internet traffic to `198.19.0.1` on `utun4`, which is a dead virtual interface. All outbound TCP connections black-holed.

### Fix
```bash
sudo route delete -net 128.0.0.0/1
```
(Not yet applied — user was asked to run this)

### Lessons Learned

1. **Always check system connectivity FIRST** before blaming the app. A simple `curl https://httpbin.org/ip` would have saved 30+ minutes of dead-end troubleshooting.

2. **Split-routing VPN residue is stealthy.** DNS works (uses different path), proxy process is gone, but routes persist until manually deleted.

3. **"Zero outbound TCP" has two causes:**
   - App process network dead (original hypothesis)
   - System routing black hole (actual cause today)
   
4. **The diagnostic order matters.** System check → app check, not the other way. The `todesk-remote-fix` v2.0 skill now enforces this.

5. **Passwordless sudo is essential for remote fixes.** Without it, even once the root cause is known, the agent is helpless.
